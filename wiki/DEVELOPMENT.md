# Устройство Spice Sifter 0.5

Публичный интерфейс — `python spice_sifter.py test.json`. Инструкции и ограничения — в [руководстве пользователя](User-Guide.md). Результаты версии 0.4 — в [SWEEP_VERIFICATION.md](SWEEP_VERIFICATION.md), версии 0.3 — в [TEMPERATURE_VERIFICATION.md](TEMPERATURE_VERIFICATION.md), версии 0.2 — в [AC_VERIFICATION.md](AC_VERIFICATION.md); исторический отчёт MVP 1 — в [VERIFICATION.md](VERIFICATION.md).

## Поток данных

1. Загрузка и проверка JSON, включая AC-проверки и запросы графиков.
2. Подготовка NSX: сохранение исходных директив, подключение моделей после заголовка, добавление отсутствующего `.END`.
3. Проверка основного процесса выбранного X2.EXE. Вспомогательные процессы `-R` не считаются открытым Altium.
4. Файловая блокировка и отдельный `%TEMP%/SpiceSifter/<run_id>`.
5. Генерация ASCII DelphiScript без BOM с процедурой RunTests; пути с Unicode представлены символьными литералами.
6. Открытие свободного NSX и вызов `ADVSIM:RunSimulator`.
7. Сохранение SDF текущего запуска, публикация статуса через временный файл и переименование.
8. Собственный SDF-парсер, проверки исходных массивов, затем необязательный экспорт графиков.
9. Один JSON-ответ; коды завершения PASS=0, FAIL=1, ERROR=2.

Проекты Altium и постоянные компоненты не создаются. Пользовательские документы не сохраняются и не закрываются. Параллельные симуляции не поддерживаются.

## Протокол Altium

Используются `WorkspaceManager:OpenObject`, `ADVSIM:RunSimulator` и `ScriptingSystem:RunScriptFile`. Строка запуска X2 передаётся без оболочки с нативным экранированием Altium. Код выхода вспомогательного процесса не подтверждает завершение моделирования.

`SAVE_PENDING` означает необходимость отдельного сохранения после возврата управления MixedSim. Допускается ровно один дополнительный скрипт сохранения. Окончательные статусы — `OK` и `ERROR`; путь SDF должен точно совпадать с ожидаемым файлом внутри каталога текущего запуска.

После тайм-аута процесс Altium не завершается. `pending-run.txt` блокирует последующие вызовы, пока прежний запуск не опубликует окончательный статус. Порядок проверки защищён общей блокировкой. Восстановление после зависания описано в README.

## Числовые данные

`SDFDocument` содержит Chart и метаданные, `SDFChart` — Wave, `SDFWave` — название, единицу, тип, число точек и полные массивы X/Y. Комплексные значения представлены Python complex.

Парсер SDF 1.0 использует размеры блоков из WavePoints и признаков комплексности. Действительная точка содержит float64 X/Y; комплексная X/Y — Re(X), Im(X), Re(Y), Im(Y). После основного блока читается соответствующий вспомогательный блок float32. Проверяются границы, завершённость и TotalPoints. Неизвестный формат не угадывается.

Валидатор выбирает Chart по анализу и требуемым сигналам; неоднозначность отклоняется. Для AC проверяются конечность, положительный строго возрастающий порядок частот и совпадение сеток V/I. При интерполяции сначала вычисляются V(f), I(f), затем Z=V/(current_sign·I). Допуски проверяются на исходных данных.

Экспорт формирует синхронизированные массивы real/imag/magnitude с единицами. Для действительных сигналов экспортируется только real. Ограничение max_points применяется к выходным индексам и не изменяет данные валидатора. Графики возвращаются при FAIL; без запроса поле graphs отсутствует.

## Температурный слой 0.3

Перед прежним Runner работает планировщик execute_test: разбирает температурные директивы, валидирует ссылки проверок/графиков и последовательно вызывает execute_one для каждой температуры. Парсер SDF не менялся. Температура привязывается к уникальному run_id, а не угадывается из SDF. Данные и интерполяция AC разных запусков не смешиваются.

В Altium 24.4 подтверждена альтернатива `.OPTIONS TEMP`, поскольку прямая `.TEMP` не изменила параметры контрольного диода. Подстановка выполняется в generate_nsx после валидации внешнего `.TEMP`. TNOM и файлы моделей не меняются. Варианты серии добавляют температурную директиву сразу после заголовка, вне вложенных блоков.

Графики помещаются в runs[i].graphs; результаты с ошибками не уничтожают остальные элементы runs. Блокировка и pending-run.txt остаются общими; тайм-аут не приводит к принудительному завершению Altium. Подробнее: TEMPERATURE_VERIFICATION.md.


## Parameter Sweep 0.4

parameter_axes разбирает список или компактное описание линейной оси. sweep_plan вычисляет полное произведение с температурами, проверяет max_runs, when, плейсхолдеры и подготовленные схемы до первого процесса Altium. Десятичная арифметика исключает накопление ошибки шага; огромные линейные сетки не разворачиваются до проверки лимита.

execute_sweep перебирает температуры и декартово произведение индексов, подставляет выбранные Decimal-значения, фильтрует проверки/графики и вызывает прежний execute_one. Контекст параметров связывается с run_id вне SDF-парсера. execute_one сохраняет старую структуру ответов при отсутствии sweep; отдельная температурная серия также не меняется.

require_running_altium дополнительно читает Responding основного процесса: неотвечающий Altium даёт BUSY. Это чтение состояния процесса, без управления интерфейсом. Подробности и реальная приёмка — SWEEP_VERIFICATION.md.


## Measurement Engine 0.5

validate_measurements проверяет фиксированную схему запросов до Altium. process_measurements вызывается после чтения полного SDF и до сокращения графиков. measure_value работает только с SDFDocument: не обращается к Runner, файлам, моделям или симулятору. Limits проверяются прежним validate; вторая логика допусков не вводилась.

Для sweep_crossing каждый подходящий запуск сохраняет только скалярную редукцию сигнала во внутреннем временном контексте. finish_measurements группирует значения по температуре, проверяет полноту/однозначность и формирует верхнеуровневые результаты. Держать все осциллограммы серии в памяти не требуется. Внутренние поля удаляются перед JSON.

Одиночные измерения имеют run_id; семейные — scope=sweep и run_ids. Общий статус дополнительно учитывает измерения, прежние checks/runs/graphs/summary сохраняются. Формат — MEASUREMENTS.md, проверка — MEASUREMENT_VERIFICATION.md.


## DbLib Component Mode

Второй режим включается наличием `component` во входном JSON. `dblib_runner.py` выполняет предварительную проверку библиотеки и таблицы, копирует неизменяемый шаблон `dblib_resources/template` в `temp/dblib_runs/<run_id>/`, подставляет пути в `dblib_resources/dblib_experiment.pas` и запускает его в уже работающем Altium. Standalone-режим и его Runner не изменяются; оба режима используют общую блокировку `altium_session()` и общий `pending-run.txt`.

DelphiScript вызывает `SchServer.LoadComponentFromDatabaseLibrary`, размещает `ISch_Component` через `MoveToXY`/`RegisterSchObjectInContainer`, вычисляет hotspot выводов, создаёт короткие Wire и Net Label, компилирует проект и проверяет принадлежность выводов DUT цепям `DUT_P`/`GND`. Затем Altium генерирует NSX из SchDoc, а второй вызов `ADVSIM:RunSimulator` по этому NSX создаёт SDF. Координатный fallback очистки `X >= 4000` не используется: удаляются только объекты из журнала текущего запуска (DUT UniqueID, Wire, Net Label). Очистка выполняется и при FAIL/ERROR; документы Altium не закрываются.

Python дополнительно проверяет источник компонента, ID, таблицу, два вывода, SIM Implementation и Port Map, NSX (ровно один DUT, `.SUBCKT`, порядок цепей) и актуальность NSX/SDF по каталогу и времени запуска. Проектный SDF может содержать несколько одинаковых chart setups; для вызова прежнего Validator они схлопываются по анализу и набору сигналов. Далее используются только существующие `parse_sdf()`, `validate_document()`, `process_measurements()`, `finish_measurements()` и `export_graphs()`.

Поддерживается одиночное испытание; `sweep`, `temperatures_c` и `when` в DbLib-режиме отклоняются до запуска. Ресурсы режима и шаблон входят в репозиторий; рабочие копии создаются только в `temp`. Тесты: `tests/test_dblib.py` (без Altium) и `tests/acceptance_dblib.py` (реальная библиотека `MY_LIB.DbLib`).
