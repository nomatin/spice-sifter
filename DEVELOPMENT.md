# Устройство DBUR Test 0.2

Публичный интерфейс — `python dbur_test.py test.json`. Инструкции и ограничения — в [README.md](README.md). Результаты проверки версии 0.2 — в [AC_VERIFICATION.md](AC_VERIFICATION.md); исторический отчёт MVP 1 — в [VERIFICATION.md](VERIFICATION.md).

## Поток данных

1. Загрузка и проверка JSON, включая AC-проверки и запросы графиков.
2. Подготовка NSX: сохранение исходных директив, подключение моделей после заголовка, добавление отсутствующего `.END`.
3. Проверка основного процесса выбранного X2.EXE. Вспомогательные процессы `-R` не считаются открытым Altium.
4. Файловая блокировка и отдельный `%TEMP%/DBUR-Test/<run_id>`.
5. Генерация ASCII DelphiScript без BOM с процедурой RunTests; пути с Unicode представлены символьными литералами.
6. Открытие свободного NSX и вызов `ADVSIM:RunSimulator`.
7. Сохранение SDF текущего запуска, публикация статуса через временный файл и переименование.
8. Собственный SDF-парсер, проверки исходных массивов, затем необязательный экспорт графиков.
9. Один JSON-ответ; коды завершения PASS=0, FAIL=1, ERROR=2.

Проекты Altium и постоянные компоненты не создаются. Пользовательские документы не сохраняются и не закрываются. Параллельные симуляции не поддерживаются.

## Протокол Altium

Используются `WorkspaceManager:OpenObject`, `ADVSIM:RunSimulator` и `ScriptingSystem:RunScriptFile`. Строка запуска X2 передаётся без оболочки с нативным экранированием Altium. Код выхода вспомогательного процесса не подтверждает завершение моделирования.

`SAVE_PENDING` означает необходимость отдельного сохранения после возврата управления MixedSim. Допускается ровно один дополнительный скрипт сохранения. Окончательные статусы — `OK` и `ERROR`; путь SDF должен точно совпадать с ожидаемым файлом внутри каталога текущего запуска.

После тайм-аута процесс Altium не завершается. `pending-run.txt` блокирует последующие вызовы, пока прежний запуск не опубликует окончательный статус. Порядок проверки защищён общей блокировкой. Восстановление после зависания описано в README.

## Числовые данные

`SDFDocument` содержит Chart и метаданные, `SDFChart` — Wave, `SDFWave` — название, единицу, тип, число точек и полные массивы X/Y. Комплексные значения представлены Python complex.

Парсер SDF 1.0 использует размеры блоков из WavePoints и признаков комплексности. Действительная точка содержит float64 X/Y; комплексная X/Y — Re(X), Im(X), Re(Y), Im(Y). После основного блока читается соответствующий вспомогательный блок float32. Проверяются границы, завершённость и TotalPoints. Неизвестный формат не угадывается.

Валидатор выбирает Chart по анализу и требуемым сигналам; неоднозначность отклоняется. Для AC проверяются конечность, положительный строго возрастающий порядок частот и совпадение сеток V/I. При интерполяции сначала вычисляются V(f), I(f), затем Z=V/(current_sign·I). Допуски проверяются на исходных данных.

Экспорт формирует синхронизированные массивы real/imag/magnitude с единицами. Для действительных сигналов экспортируется только real. Ограничение max_points применяется к выходным индексам и не изменяет данные валидатора. Графики возвращаются при FAIL; без запроса поле graphs отсутствует.

## Проверка и файлы проекта

- `tests/test_*.py`: автономные тесты, включая реальные SDF в `tests/fixtures`.
- `tests/acceptance.py`: реальная регрессия MVP 1 с открытым Altium.
- `tests/acceptance_ac.py`: реальная AC-приёмка и проверка экспорта.
- `examples/`: делитель, диод с внешней моделью, AC R/C/L/RC, полный и ограниченный экспорт.
- `diagnostics/` и локальные JSON-отчёты приёмки исключены из Git; исходные модели и SDF-образцы тестов хранятся в репозитории.
